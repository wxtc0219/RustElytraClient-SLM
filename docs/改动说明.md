# 改动说明（技术细节）

目标 jar：`RustElytraClient-1.21.1-beta1.6-260502_1913.jar`（官方 beta1.6 发行版）
产物：`RustElytraClient-1.21.1-beta1.6-slm-takeover-1.0.0.jar`

全部修改通过 ASM（`asm-tree` 9.10.1）直接改写字节码完成，未接触源码（上游 beta1.6 源码可从提交 `b7f60332` 取得）。
每个改过的类都用 ASM `BasicVerifier` 逐方法做数据流/栈一致性校验，结果全部 OK。

## 1. `dev/rstminecraft/TaskThread$TaskType` — 新增第 4 个枚举常量

原枚举：

```java
EXP_BOTTLE, ELYTRA, INFINITY_ELYTRA
```

修改后：

```java
EXP_BOTTLE, ELYTRA, INFINITY_ELYTRA, SLM_TAKEOVER
```

实现步骤（`Patch4.java` 的 `enum` 模式 + `Patch6.java`）：

1. 新增字段 `public static final TaskThread$TaskType SLM_TAKEOVER`
2. `<clinit>`：在 `INFINITY_ELYTRA` 的 `PUTSTATIC` 之后插入
   `NEW / DUP / LDC "SLM_TAKEOVER" / ICONST_3 / INVOKESPECIAL <init>(String,int) / PUTSTATIC`
3. `$values()` 是独立的合成方法（不是 `<clinit>`）：把 `ICONST_3` 改 `ICONST_4`，
   在 `ARETURN` 前插入 `DUP / ICONST_3 / GETSTATIC SLM_TAKEOVER / AASTORE`

> 注意：`InsnList.insert(location, insns)` 在此版本 ASM 中会把指令插到 `location` **之后**，
> 要插在前面必须用 `insertBefore`。Patch6 就是用来修正第一次误插到 `ARETURN` 之后的残留。

## 2. `dev/rstminecraft/RustElytraClient$1` — 让新常量复用 ELYTRA 分支

该类是 javac 生成 `$SwitchMap$...TaskType` 的合成类。原逻辑：
`$SwitchMap[ELYTRA.ordinal()] = 1; $SwitchMap[EXP_BOTTLE.ordinal()] = 2; $SwitchMap[INFINITY_ELYTRA.ordinal()] = 3;`

补丁在 `<clinit>` 的 `RETURN` **之前**（必须用 `insertBefore`，`insert` 会插到 `RETURN` 之后变成死代码）追加：

```java
$SwitchMap$dev$rstminecraft$TaskThread$TaskType[SLM_TAKEOVER.ordinal()] = 3;
```

> 踩坑记录：第一版误用 `insert`，赋值成了 `return` 之后的死代码，导致 SLM 在 switch 里走 default：
> 补给计算出 `FireworkInNeed = 0 / ElytraInNeed = 0` 后直接 return，**完全不去取物资**。
> 现已改为 `insertBefore` 并在反编译中确认为 `148: iastore / 149: return` 的顺序。

映射到 **`INFINITY_ELYTRA` 分支（值 3）** 而不是 ELYTRA（值 1），对甲飞更合适：

- 补给目标烟花 **1664**（ELYTRA 分支是 1344），且 `ElytraInNeed = 0` —— **不要求鞘翅**
- `RustElytraTask.ElytraTask` 中 `type == INFINITY_ELYTRA` 会关闭 `elytraAllowEmergencyLand` —— 甲飞不应自动紧急降落
- 也不会走 `type == ELYTRA` 的 `ElytraChecker`（那是给真鞘翅准备的检查）

> ⚠️ 第二个坑：`switch(type)` 的映射表是**每个类各自一份合成类**。
> `RustElytraClient` 用 `RustElytraClient$1`，但 **`RustSupplyTask` 用的是 `RustSupplyTask$1`**（各自持有 `$SwitchMap$...$TaskType` 字段）。
> 只补 `RustElytraClient$1` 会导致补给阶段仍走 default：`FireworkInNeed = 0 / ElytraInNeed = 0` → `SupplyTask` 直接 return，**完全不去取物资**。
> 因此最终的 jar 对 **两个合成类** 都做了同样的映射（可在运行时反射验证：两者的 `map[3]` 都必须等于 3）。

## 3. `dev/rstminecraft/RSTScr$ciScr` — 菜单加第 4 个按钮

`ciScr` 构造函数里有一句：

```java
this.entry = new SrcEntry[]{ X输入, Z输入, 按钮1(ELYTRA), 按钮2(EXP_BOTTLE), 按钮3(INFINITY_ELYTRA) };
```

`RSTSimpleScr` 用 `this.entry` 数组渲染按钮（子类构造完才赋值，所以 `init()` 时能读到）。

修改（`Patch4.java` 的 `gui` 模式）：

1. 构造器内 `ICONST_5` → `BIPUSH 6`（数组长度 + super 的行数参数）
2. 复制“ELYTRA 按钮”的 lambda 方法 → 新方法 `lambda$new$2$slm`
   * lambda 是**实例方法**（`private void lambda$new$2()`），通过 `invokedynamic run:(LciScr;)Ljava/lang/Runnable;` 捕获 `this`
   * 复制后把其中的 `GETSTATIC TaskType.ELYTRA` 改成 `GETSTATIC TaskType.SLM_TAKEOVER`
3. 在 `PUTFIELD entry` **之前**（`insertBefore`）插入第 6 个元素：

```
DUP / BIPUSH 5 / NEW SrcButtonEntry / DUP
LDC "开始飞行(SLM甲飞接管)" / LDC "用 SlimefunHelper 甲飞驱动 baritone：不穿鞘翅、不掉耐久"
ALOAD 0                      ← 关键：实例 lambda 必须把 this 压栈
invokedynamic run:(LciScr;)Ljava/lang/Runnable;
INVOKESPECIAL SrcButtonEntry.<init>(String,String,Runnable)
AASTORE
```

> 踩坑记录：遗漏 `ALOAD 0` 时，打开菜单会抛
> `ArrayIndexOutOfBoundsException: Index 7329008 out of bounds for length 324`（栈错位把垃圾当下标）。

## 4. `dev/rstminecraft/RustElytraTask.RepairElytra` — SLM 模式短路

原方法（节选）：

```java
private static void RepairElytra(class_310 client, int x, int z) {
    if (client.field_1724 == null || ...) throw new TaskException("null!");
    if (noElytra) return;
    class_1799 ElytraStack = client.field_1724.method_31548().method_7372(2);   // 胸甲槽
    if (ElytraStack.method_7909() != class_1802.field_8833) {                    // 不是鞘翅
        throw new TaskException("未穿戴鞘翅!");
    }
    ... 修鞘翅 / 附魔之瓶补给 ...
}
```

补丁（`Patch8.java`）在方法入口插入：

```
INVOKESTATIC T.isSlm:()Z
IFEQ  skip
RETURN
skip: FRAME F_SAME        ← 方法入口栈为空、局部变量即参数，所以是 same frame
<原作者逻辑>
```

效果：SLM 模式直接跳过整套“必须穿鞘翅”的修复流程；其余三个模式**逐字节保持原版**。

## 5. `dev/rstminecraft/RustSupplyTask` — 补给前置检查

原逻辑（`SortAndCheckInv` ↗ 其 lambda）计算：

```java
class_1799 s = ...getStack(38);   // 胸甲槽
boolean elytra = s.getItem() == Items.ELYTRA
              && (!isXP || 有经验修补)
              && 有耐久3;
...
if (!elytra) throw new TaskException("物资不足：需要穿戴 耐久3 经验修补的鞘翅！");
```

补丁（`Patch7b.java`）在守卫跳转前插入 `INVOKESTATIC T.elytraOk:(Z)Z`，即：

```java
if (!T.elytraOk(elytra)) throw ...
```

`T.elytraOk(wornOk)` 语义：

| 当前任务 | 返回值 |
| --- | --- |
| 其它三个模式 | `wornOk`（= 原版行为） |
| `SLM_TAKEOVER` | `wornOk \|\| 背包里有鞘翅` |

同时保留了之前对补给流程的两处修正（`Patch2.java`）：

* `ContainerScreenChecker`：`String.equalsIgnoreCase` → `T.eq`（去掉 `§` 颜色码、双向包含匹配，兼容服务端/插件改名后的容器标题）
* `WaitForScreen`：循环上限 `20` → `120` tick（等待容器界面打开的时间放宽）

## 6. `dev/rstminecraft/T` — 运行时辅助类（新增）

| 方法 | 说明 |
| --- | --- |
| `eq(String, String)` | 容器标题宽松比较（去颜色码、小写、双向包含） |
| `isSlm()` | 反射读 `TaskThread.getModThread().type`，判断是否 `SLM_TAKEOVER` |
| `hasElytra()` | 反射取 `MinecraftClient.getInstance().player.getInventory()`，扫 0–40 格找 `Items.ELYTRA` |
| `elytraOk(boolean)` | `wornOk \|\| (isSlm() && hasElytra())` |
| `repairGuard(Object)` | 备用：胸甲槽物品是鞘翅或当前为 SLM 模式 |

反射使用的 intermediary 名（MC 1.21.1）：
`class_310.method_1551`（getInstance）、`class_310.field_1724`（player）、
`class_XXX.method_31548`（getInventory）、`method_5438`（getStack(int)）、
`method_7909`（getItem）、`class_1802.field_8833`（Items.ELYTRA）。
